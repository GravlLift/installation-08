See `third_party/README.md` and the upstream license and notice files for provenance.

The files-reader module includes the GPL-3.0 `ooz` decompressor; see `third_party/files-reader/ooz/NOTICE.md`. No game assets are distributed. Game-derived assets (map meshes) are built from the user's own installation.

`internal/mapmesh`, `internal/meshbuild` and `internal/mapref` are adapted from LevelUp's `internal/mapmesh` and `cmd/mapmesh-build` (AGPL-3.0, JGtm), rewritten to resolve and build a map mesh, a variant's object layer, a weapon model, the Spartan body, a single armor piece and a weapon's first-person rig in-process instead of through a child process and its own wire protocol. `internal/mapref` embeds reference data copied unmodified from LevelUp's `data/titles/halo_infinite/reference/` (the objectives catalog, the per-map background sidecars, the per-map geometry settings, the Forge material tints catalog `forge_materials.json` ~164 KB, and the Forge object visibility catalog `forge_objects.json` ~3.8 MB): measurements and catalogs built from publicly downloadable UGC map variants, not extracted from a local game installation. The variant builder's `--forge-materials` and `--forge-objects` flags override these embedded defaults with a different file when given; they are optional precisely because the defaults are shipped in the binary.

`internal/refdata/data/map_quant_bounds.json` is the map quantization bounds catalog (map display name, world bounds and per-axis quanta widths), copied from LevelUp's catalog producer `cmd/mapquant-build` and its measured catalogs (AGPL-3.0, JGtm): the bounds are measurements of the game's own level geometry (a map's own module, or its Forge canvas), not extracted assets. `internal/refdata/data/map_identity.json` is the map identity table keyed by the map asset id the film writes in chunk_00: display name, the normalized bounds-catalog key (the decoder's `NormalizeMapName` is the single rule from display name to key), and the geometry module key. It is generated from three LevelUp reference files (AGPL-3.0, JGtm): `.ai/V7.5/cartes/inventaire_rotation_ugc_2026-08-27.json` (the matchmaking rotation inventory: 104 maps with display name, module or Forge canvas), `apps/go-api/internal/service/testdata/map_ids_joues_20260827.json` (the map asset ids of played matches, frozen 2026-08-27, display names only), and the name-to-module table written in `apps/go-api/cmd/mapquant-build/main.go` (the level_id proofs that key the bounds catalog). The table holds 171 asset ids; 148 resolve to a bounds entry, 170 to a module key; the 23 without a bounds entry and the 1 without a module key (list in `TestMapIdentityCoverage`) degrade to a `--map` prompt or an unproven module, never a wrong decode.

`internal/mapmesh/spartan.go`'s `BodyAnimations` list is copied from LevelUp's `internal/mapmesh/meshproto` (`animationsDuCorps`, the body-only prefix of its `AnimationsSpartan`): names are the game's own animation identifiers, not game assets. Armor piece coatings (the community Ekur reference, a Blender plugin's JSON export external to both LevelUp and this repo) and the per-weapon third-person reload/fire animation catalog are not ported; see README.md's build-piece and build-spartan sections.

`internal/weapons` builds the whole weapon library (every `weap` tag of the installed game, the grenade projectiles, and the Spartan body) by reusing the same per-model builders `internal/mapmesh` already uses for `build-weapon` and `build-spartan`; it copies no additional game data and embeds no new reference files. The roster it reads is the game's own `weap` tags, exposed by a LOCAL-CHANGE in the vendored `himap` module (`third_party/map-images/himap/arsenal_roster.go`, registered in `third_party/README.md`). Built GLBs land in the data directory (gitignored), never in the repo.
